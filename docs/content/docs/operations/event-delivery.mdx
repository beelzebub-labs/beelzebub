description: Retain optional Platform events on disk and recover pending delivery after sensor restarts.

## Enable Durable Delivery

Durable delivery is opt-in for Cloud event reporting. Set `BEELZEBUB_EVENT_SPOOL_DIR` to a persistent, writable directory and enable the existing Cloud integration with its URI and token. An unset or empty spool directory preserves the existing delivery behavior. Configuration retrieval and configuration polling behavior are unchanged; this option addresses event delivery only.

| Variable | Default | Behavior |
| --- | --- | --- |
| `BEELZEBUB_EVENT_SPOOL_DIR` | Empty; disabled | Persistent spool directory; the deployment examples use `/var/lib/beelzebub/events` |
| `BEELZEBUB_EVENT_SPOOL_MAX_BYTES` | `1073741824` (1 GiB) | Storage budget including pending, temporary, and quarantined records |
| `BEELZEBUB_EVENT_SPOOL_MAX_RECORDS` | `100000` | Record budget including pending, temporary, and quarantined records |

Use one sensor process per spool. Give the sensor's runtime user read, write, and directory traversal permission on the mount, and read/traversal access to its ancestors for directory syncing. New directories use mode `0700` (with inherited setgid where applicable), and new records use `0600`; treat their contents as sensitive captured traffic. Existing directory permissions are preserved. A non-root deployment must provision the volume with the correct ownership or a compatible Kubernetes `fsGroup`; a root-owned, group-writable mount with mode `02775` is supported without requiring the sensor to chmod it. Restrict the mount's group to trusted operators. Avoid network filesystems unless their locking, atomic rename, and fsync guarantees are established. The volume must have enough free space for the configured budget and filesystem overhead.

## Delivery And Retry Behavior

Capture assigns each new durable event a stable UUIDv7 EventKey, preserving the session ID as a separate field. Supplied keys, including UUIDv4 keys, are preserved. The event passes through synchronous durable storage before capture reports acceptance; the upstream tracer memory queue does not acknowledge it first. Initialization creates missing spool ancestors from the root down and syncs each parent entry before proceeding, including existing entries that an earlier interrupted initialization may have left unsynced. A directory-sync failure prevents startup and acceptance. New records retain the original serialized request in a versioned envelope. Writes sync the file, rename it atomically, and sync the directory before acceptance. The delivery worker replays pending records after restart and preserves the payload and identity across retries.

One delivery worker selects the oldest pending records in batches of at most 16,384 filenames and ordering metadata, independently of the spool capacity. UUIDv7 records are ordered by the timestamp and monotonic sequence encoded in their keys, without reading payloads for sorting. Older UUIDv4 envelopes and raw cloud-patch records use their stored capture timestamps at millisecond precision, with EventKey as a deterministic tie-breaker. Records without usable ordering metadata are handled first so corrupt records can enter quarantine. Neither stored keys nor payloads are rewritten to establish order.

The worker drains each sorted batch before scanning again. An unacknowledged head record is retried before later records; retries retain the batch without rescanning the backlog. Captures arriving during a batch are considered on the next scan. Sorting and payload reads for legacy ordering run outside the capture mutex, and enqueue does not scan or sort the backlog.

Events are submitted approximately in capture order per sensor. The UUID generator is monotonic within a process, including within the same millisecond, but clock changes across restarts, supplied keys, concurrent captures becoming durable at different times, and batching can affect order. Downstream asynchronous processing can also reorder accepted events. This is not a guarantee that a session start is processed before its end; strict session ordering requires explicit sequencing and downstream enforcement.

HTTP 200 acknowledges an event. If the response supplies an EventKey, it must match the pending event before removal. For compatibility, legacy HTTP 200 responses without EventKey also acknowledge delivery; this cannot establish server-side durability or deduplication. Other success statuses are retained for investigation and retry.

Acknowledgements may contain the full accepted EventDTO, including large captured fields. The worker reads their JSON incrementally and checks the top-level EventKey regardless of its position. Its response byte budget scales with the posted event, allowing sixfold JSON escaping expansion plus 64 KiB of envelope headroom. An incomplete, mismatched, or oversized response leaves the original event queued.

Requests time out after ten seconds. Network failures, HTTP 408, 429, and 5xx retry with exponential backoff and jitter from one to thirty seconds. Valid `Retry-After` guidance can delay retries up to fifteen minutes. HTTP 401/403 and unexpected statuses retain the record and retry slowly, every sixty seconds, with actionable diagnostics. Logs exclude credentials and response bodies.

HTTP 400/409/413/422 preserves the original record in `quarantine/` and allows later pending records to proceed. The filename records its rejection reason and HTTP status. Corrupt records and incomplete temporary writes are also retained in quarantine; complete temporary writes are recovered. Quarantine is diagnostic storage and is not automatically resubmitted. A quarantine move is complete only after the quarantine directory and then the source spool directory synchronize successfully. A failed synchronization remains pending even though the source filename has disappeared. Replay retries the barriers before advancing, and new captures wait within their admission budgets rather than syncing past the incomplete move. Startup synchronizes existing quarantine state before accepting captures or replaying records; persistent synchronization errors prevent initialization with an explicit storage error. Storage recovery resumes capture and replay without resubmitting quarantined records.

Disk errors and a full byte or record budget apply cancellation-aware capture backpressure within a bounded admission budget. An individual event larger than the entire configured byte budget fails capture explicitly. Shutdown cancels pending HTTP requests and waits without requiring the remote API to recover. Events that have not reached durable acceptance can still be lost on termination; producers must observe capture failures. Accepted pending events remain on disk.

Before DTO conversion or JSON serialization, each spool limits active and waiting captures to 256 events and a combined 64 MiB conservative memory estimate. The estimate includes source fields, metadata entries, JSON escaping, and encoding scratch space; larger events consume more budget. Acquiring capacity never waits: an exhausted budget or an individually oversized capture returns an explicit error, counted by `beelzebub_capture_failures_total` through the tracer, even if disk space remains. A reservation covers serialization, filesystem writes, and storage/capacity waits, and is released on every return path. Cancellation, shutdown, or memory pressure releases blocked captures; storage recovery lets captures within the budget proceed. Persisted records and the independent replay worker do not consume this capture budget. These limits bound admission retention rather than all HTTP parsing or process memory.

An additional filesystem watermark stops new spool writes when available space reaches twenty percent of the filesystem's total capacity. It includes other files and space reserved from the sensor's user, and checks the prospective record's growth rounded to allocation blocks. Configured byte and record limits still apply if reached earlier. A failed capacity measurement also pauses admission. Existing records remain queued and delivery continues so it can release space; admission resumes when space recovers. The check runs on the spool's filesystem, including a dedicated volume or tmpfs, rather than a host-wide disk estimate.

HTTP and MCP capture use the request context; SSH uses its session or authentication context. Ordinary TCP capture observes its service context and configured connection deadline, and TELNET capture observes its configured session deadline. TCP attempt events emitted after a read ends, final buffered interactions, and TCP/SSH/TELNET session-end events get a fresh five-second capture window so an expired connection context does not discard teardown evidence. Closing the spool still cancels that capture immediately. Producer cancellation releases durable captures waiting on unavailable storage or capacity, after their first admission attempt. Once an event is durably accepted, producer cancellation does not cancel its independent delivery worker. Existing tracer implementations remain supported; context-aware tracers implement the optional `ContextTracer` interface and producers bind their lifetime with `tracer.WithContext`.

Within the capture budgets, a completed event gets one durable admission attempt even when the client has already disconnected. If storage is writable and has capacity, that attempt persists it before returning. A full or unavailable spool still uses the producer context to stop waiting; shutdown rejects further admission. Cancellation does not interrupt an in-progress filesystem write or fsync. `beelzebub_capture_failures_total` counts admission failures separately from the existing accepted-event counters; failures also produce a diagnostic without captured bodies or credentials.

Legacy Cloud reporting reuses one HTTP client and connection pool for the sensor lifetime. Requests have a ten-second timeout, and shutdown cancels active requests and closes idle connections.

Without the disk spool, a completed event uses the existing five-slot memory queue independently of the client connection. Up to 256 producers can wait for a slot. Of those, at most sixteen can continue waiting after capture observes producer cancellation or expiry, including clients that disconnect after they start waiting. Connected clients use the overall budget without consuming the disconnected retention budget. When a waiting client disconnects, its capture must claim a disconnected slot; if that budget is full, capture fails explicitly. A full overall waiting budget also rejects additional waiting events immediately. Every rejected capture increments `beelzebub_capture_failures_total` once. Waiting continues while workers dequeue events; five seconds without observed dequeue progress ends admission with an explicit timeout. This is a stall limit, not an overall delivery deadline. Healthy but slow delivery can therefore take longer than five seconds while the waiting budget has room. Available queue slots still accept events directly when memory headroom permits.

On Linux, new durable and memory-only admission, and their continuing waits, also require more than twenty percent memory headroom. Host pressure uses `MemAvailable` relative to `MemTotal`, so reclaimable cache is not simply counted as unavailable RAM. Visible cgroup v1/v2 limits and their parent limits are checked against the estimated working set, including other processes in those groups. The sensor subtracts reclaimable inactive file cache from raw cgroup usage (`total_inactive_file` in cgroup v1, `inactive_file` in v2), clamping at zero if separately read counters race. Ordinary file caching therefore does not by itself exhaust the memory admission budget. Reaching eighty percent working-set usage, or failing to read required measurements, rejects admission or releases a waiter with an explicit capture failure; later captures retry fresh measurements. Other operating systems emit a diagnostic and retain both waiter limits without a memory-percentage check. The durable tracer bypasses these volatile waiting limits.

These are admission limits, not operating-system resource reservations. Request parsing, already accepted events, filesystem metadata, and other processes can allocate after a measurement. They reduce overload risk but cannot guarantee that the machine always retains twenty percent free memory or disk space. Memory-only delivery still has no restart durability or API retry guarantee, and unlimited incoming traffic cannot be guaranteed lossless with finite storage and memory. Payload sizes also affect memory usage; a waiter count is not a byte limit.

The sensor counts retained bytes and records at startup, then updates those totals as writes and removals happen. Capturing an event does not enumerate the backlog or quarantine. A separate worker reconciles filesystem usage without holding the capture mutex, once per minute and on capacity pressure, with pressure scans limited to one per second. A scan racing a write or removal is discarded and retried. Moving resolved quarantine records out of the spool therefore releases capacity after reconciliation; do not add or rewrite spool records while the sensor is running.

## Restart And Identity Guarantees

Delivery is at least once after durable acceptance. Pending events survive process crashes, SIGKILL, and container recreation when the same persistent storage is retained. Deleting the volume, permanent disk loss, and failures before durable acceptance are outside that guarantee. Storage hardware must honor fsync.

A server can accept an event before its HTTP acknowledgement is lost, or the sensor can crash after acknowledgement before durable removal. Both cases can replay the same EventKey. A compatible Platform deduplicates unchanged events using that identity; legacy servers and downstream effects can produce duplicates. This sensor option does not promise exactly-once processing or durable storage within other services.

Retain the same Platform endpoint and sensor token while replaying a backlog. New spool records bind replay to the original endpoint/token identity without storing credentials. A changed identity holds those records for operator intervention. Restore the original configuration to resume delivery; do not edit identities or generate replacement keys blindly. A Platform that binds idempotency to the sensor token can reject replay under a replacement token. Drain the spool before rotating tokens where possible. Legacy raw JSON records from the cloud sensor patch are readable and bind to the current configuration because they lack stored endpoint/token identity.

## Operator Recovery

Monitor pending age and count, quarantine growth, filesystem free space, and delivery diagnostics. A running worker does not establish successful delivery. Preserve records and their volume while restoring connectivity, credentials, storage access, or capacity. Increasing the budget requires enough underlying volume capacity and a sensor restart with the updated limits.

Inspect rejected or corrupt records only through restricted tooling; never paste captured credentials or payloads into logs or public reports. Keep an original copy before repair. Quarantine contributes to capacity, so move resolved diagnostic records to protected archival storage under an explicit retention policy. Correct the rejection cause before deliberately replaying a record, retaining the original event key, payload, endpoint, and token. Do not purge pending files to clear an alert.

Use the [Compose override](/operations/docker#durable-cloud-events) or [Helm persistence options](/operations/kubernetes#durable-cloud-events) to retain the spool across container or pod replacement.
